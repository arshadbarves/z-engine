The user ran /commit: create one git commit of the current changes. This is
explicit permission to commit and nothing more. Do not push, amend, rebase,
reset, change git configuration, or skip hooks.

Notes from the user (may be empty; a message hint or the files to include):
$ARGUMENTS

## Steps

1. Run these in parallel: `git status`, `git diff`, `git diff --staged`, and
   `git log --oneline -15` to learn the message style.
2. Decide what to commit.
   - If changes are already staged, commit exactly what is staged unless the
     notes say otherwise.
   - Otherwise stage the changed and new files by path, never with
     `git add -A` or `git add .`.
   - Leave out files that look like secrets (`.env` files, keys,
     credentials), build output, and large binaries, and mention what you left
     out.
   - If there is nothing to commit, say so and stop.
3. Write the message in the repository's style. If the history uses
   Conventional Commits, use `type(scope): subject`. Keep the subject short
   (about 50 characters, 72 at most), in the imperative, with no trailing
   period. Add a body, wrapped at 72 columns, only when the reason for the
   change is not obvious. Describe what changed and why, not a list of files.
   Do not add co-author or "generated by" trailers unless the repository
   already uses them.
4. Commit with a heredoc so the formatting survives:

   ```bash
   git commit -F - <<'EOF'
   type(scope): subject

   Optional body explaining why.
   EOF
   ```

5. If a hook fails, do not bypass it. If it only reformatted files, stage them
   and commit once more. Otherwise report the hook's output and stop.
6. Run `git status` to confirm the result. Reply with the short commit hash
   and subject, and list anything left uncommitted.
