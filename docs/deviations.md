# Deviations from spec

Recorded per §10: when a requirement proves impractical, the smallest
alternative consistent with §2 constraints is chosen **and documented here**.

| # | Spec point | Deviation | Rationale | Version |
|---|---|---|---|---|
| 1 | §4.2 "No hard turn cap" | Runaway fuse at 500 consecutive tool rounds ends the turn with an error | Guards against pathological provider loops that repeat a failing call forever; far beyond any real task | v0.1 |
| 2 | §9 v1.0 `--headless` | Shipped early as a developer/acceptance flag (`--headless [task…]`, stdin when empty, `--auto-approve` companion) | Scriptable end-to-end acceptance runs need non-interactive driving; formal UX polish still lands in v1.0 | v0.1 |
| 3 | §6 token counting | Budget pressure uses provider-reported usage (prompt = latest request, completion = running total); local estimate is chars÷4 until v1.0 calibration | Avoids heavyweight tokenizer data; provider usage is authoritative for compaction decisions anyway | v0.3 |
| 4 | §5 reads "auto-allowed" | Read tools auto-allow only by tool name; path-level read restrictions are not enforced yet | Path-scoped read gating arrives with the outside-root write guard work (v0.5) where canonicalization exists; keeping v0.1 slice small | v0.5 planned |
| 5 | §9 v0.8 LSP client over stdio | Interactive rust-analyzer cannot spawn its large-stack worker thread inside sandboxed shells (jod-thread panic); harness therefore prefers the stdio JSON-RPC client when it starts, and falls back to `rust-analyzer diagnostics` batch CLI for diagnostics plus tree-sitter/grep based definition+reference resolution otherwise | Keeps compiler-grade feedback deterministic in CI/sandboxes while retaining full protocol support on developer hosts | v0.8 |
| 6 | §8 secrets via environment variables | Added a fallback that reads `~/.config/z-engine/api-key` then `~/.config/harness/api-key` (trimmed) when `ZENGINE_API_KEY` / `HARNESS_API_KEY` are unset/empty — matches the acceptance-script convention and removes the most common first-run 401 ("Missing Authentication header") | Env stays primary per spec; file is opt-in convenience | v1.0 |
| 7 | §10 one version per branch/PR | v1.1 interaction-parity work landed directly on `main` (no feature branch); tags unchanged in meaning | Single-developer session; the branch ceremony added no review value mid-stream; recorded here rather than silently ignored | v1.1 |
| 8 | §9 (post-v1.1 GUI additions) | Rewind (per-turn file checkpoints + `revert_last_turn`), `!` shell passthrough wired end-to-end, model hot-switch/context gauge/compact in the GUI, status notes routed to toasts instead of the transcript | User-requested power/UX parity with Claude Code / Codex desktop; checkpoint store is in-memory only (bash-mutated and >8 MB files are not revertible — documented limitation) | v1.1 |
| 9 | crate/product names `harness-*` | Renamed to `z-engine-*` (TUI binary `zengine`, bundle id `dev.zengine.gui`). Env (`ZENGINE_*`), config (`~/.config/z-engine`, `<project>/.z-engine`), and data dirs write to the new names; `HARNESS_*` and `.harness` paths are still read. Historical spec files under `docs/superpowers/specs/` keep the original `harness` names. | Product rebrand; fallbacks keep existing sessions and config | v1.1 |
| 10 | §9 evidence-gated mode (v1.2 slice) | Guarded runs authorize *symbol-level* changes for Rust only: a `.rs` mutation needs the work order to name a target symbol, needs rust-analyzer to place that symbol in the file, **and needs every changed line to fall inside that symbol's `documentSymbol` extent** — naming one function does not license editing the one beside it, and a whole-file `.rs` rewrite is refused because it belongs to no symbol. Other languages still get the whole gate minus the semantic step (work order, in-root path, declared scope, read evidence covering every changed line) | The claim the slice makes is "the change is the one that was authorized", and only a semantic provider can back it. Shipping the Rust seam first keeps the promise honest; other languages join by implementing `RustSemantics`' successor trait, not by weakening the rule | v1.2 |
| 11 | §9 evidence-gated mode — provider requirement | Without a reachable `rust-analyzer` (and a `Cargo.toml` at the project root) a guarded run cannot edit Rust at all: the gate refuses (`SemanticProviderUnavailable`, or `SemanticEvidenceUnavailable` when the server answers but has nothing indexed) rather than falling back to tree-sitter or grep | An outline says what the text looks like, not what the compiler sees; a fallback would authorize on weaker evidence than the mode advertises. The frozen end-to-end test *fails* where no provider answers rather than proving less; a host that cannot run rust-analyzer opts out explicitly with `Z_ENGINE_ALLOW_MISSING_SEMANTICS=1` | v1.2 |
| 12 | §9 evidence-gated mode — acceptance commands | A work order's acceptance commands may only be `cargo` invocations (`build`, `check`, `clippy`, `fmt`, `test`) with a denied-flag list; every guarded turn additionally runs `cargo check --workspace --all-targets` before it may end. **Accepted risk:** compiling model-modified Rust executes that code's `build.rs` scripts and proc-macros with the user's privileges. This is inherent to compiling as verification, not a defect in the gate — but it means a guarded run's *verification step* can run arbitrary code the model wrote, including into paths the workspace audit excludes (see row 15). Runs that cannot accept that must not enable `--guarded` on untrusted input | Verification has to be a verdict the run cannot author. Arbitrary commands would let a turn nominate its own judge; cargo is the one runner this workspace can trust offline. There is no way to compile Rust without running its build scripts, so the risk is stated rather than papered over | v1.2 |
| 13 | §9 evidence-gated mode — write surface | In a guarded run only provably read-only shell commands execute (anything else is refused as an unproven write set), and files that were never read cannot be created. Any change the run cannot attribute to a governed tool — a stray `Cargo.lock`, a bash side effect — blocks completion instead of passing silently. The proof is read off the text *before* the shell expands it, so every construct that rewrites the word list is refused outright: `$`, backticks, `<`/`>`, **and now `{ }` brace expansion, `[ ]` bracket expressions, and word-initial (or post-`=`/`:`) `~`**. `*`/`?` are the only expansions reasoned about rather than refused | A patch can be checked against evidence before it lands; a shell command's write set is known only afterwards. Fail-closed keeps the manifest an account of the whole diff, which is what makes the verdict worth anything. Brace expansion in particular defeated every option and operand rule at once (`sort {-o,out} in`, `rg {--pre,rm} foo`, `uniq {in,out}`, `env {FOO=b,cat,/etc/passwd}`), so the proof now refuses what it cannot read | v1.2 |
| 14 | §9 headless cassettes | `--record-run` / `--replay-run` / `--metrics-out` require `--headless`, and cassette paths must live outside the project directory; `--replay-run` refuses `--model` / `--base-url` and never resolves an API key | A cassette is one whole run from task to verdict, which an interactive session does not have; a tape written inside the audited tree would be an unaccounted change of the run's own making. Replay is served entirely from the tape, so reading a credential would be a lie about what it does | v1.2 |
| 15 | §9 evidence-gated mode — workspace audit | The completion audit hashes the working tree but excludes `.git`, `.hg`, `.jj`, `.z-engine`, `target/`, `node_modules/` and everything `.gitignore` covers. Inside those it audits a **bounded, explicit subset only**: every path the active order declares writable, every path a governed tool wrote, and every path the run read. Nothing else under an ignored directory is hashed, and the docs do not claim it is | Hashing a cargo target directory every turn would cost more than the run it is auditing. The exclusion is safe because the other three sides are closed: no shell command runs in a guarded run unless its write set is provably empty (row 13), every governed write is hash-checked wherever it landed, and a declared-but-ignored path is snapshotted like any other, so a check that rewrites one is a breach. What remains outside is an ignored path no order declared, no tool wrote and no read witnessed — `cargo check` writing `target/debug/**` is the intended case, and `build.rs`/proc-macro execution during verification (row 12) is the residual risk | v1.2 |
| 16 | §9 headless exit contract | A headless run exits non-zero when the agent's event channel closes without a terminal event (previously exit 0), and every run carries a finite wall-clock deadline — 30 minutes by default, `--timeout SECS` to change it. Writing `--metrics-out` can no longer change the exit code: a failed metrics write is a warning on stderr, never the run's verdict | "The agent stopped talking" and "the turn completed" are different outcomes, and a fail-closed mode that reports the first as the second verifies nothing while exiting 0. The deadline is what stops a stalled provider from holding a CI job open indefinitely; metrics are bookkeeping about a run, so they must not be able to overwrite what it decided | v1.2 |
